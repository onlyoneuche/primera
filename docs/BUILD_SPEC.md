## 1. Project context

### 1.1 What this is
A final year project (course SEN 497). The student proposed, and has defended, a system that:
1. trains and compares five classical machine learning models on a small real survey dataset about student depression,
2. selects the best model by a rule fixed in advance,
3. explains what drives its predictions,
4. deploys the best model in a single-page web check-in tool. A student answers nine questions and sees a predicted risk category with supportive, non-diagnostic wording and a list of support services in Nigeria. Nothing is stored.

### 1.2 Official aim and objectives (supervisor-approved wording; do not paraphrase in any user-facing or report-facing text)
Aim: to develop a machine learning-based early-warning system for predicting depression risk among university students.

Objectives:
1. collect dataset of students' depression risk;
2. train machine learning models for predicting students' depression risk;
3. evaluate the performance of the trained models using standard classification metrics (accuracy, precision, recall, F1-score);
4. deploy the best performing trained model in a web-based depression risk prediction system.

### 1.3 Research questions
1. What dataset of student depression risk can be collected and used for this study?
2. How can machine learning models be trained to predict students' depression risk?
3. How do the trained models perform when assessed against standard classification metrics?
4. How can the best-performing model be deployed in a web-based depression risk prediction system?

### 1.4 Who will judge this, and on what
Examiners will (a) watch a live demo of the web app, (b) read Chapter 4 (results) and Chapter 5 (conclusions), and (c) ask technical questions about methodology. Therefore:
- The interface must look polished, warm, and trustworthy. It is judged visually. Section 9 matters as much as the model.
- Every number must be real, reproducible, and explainable. Honest reporting of weak or surprising results is worth more than impressive-looking results.
- The student must be able to explain every line of code. Prefer plain, readable code over clever code.

### 1.5 Why the dataset is Malaysian (examiners asked)
The only dataset is from a Malaysian university. This is a stated scope decision, not an oversight: the study validates the modelling pipeline on a verified real dataset; validating on Nigerian data is future work because new student data collection needs ethics approval. The product must be honest about this in the UI ("About this tool") and the docs. The Nigerian relevance comes from the problem context and from localised support resources in the output.

## 2. Non-negotiable rules

1. **Never fabricate or round up results.** Report exactly what the code prints. If something is weak, say it is weak. If you cannot run something, say so.
2. **Scope is fixed.** One check-in flow, a trained model, a predicted category, a support list. Do NOT add: user accounts, login, database, history, dashboards, admin pages, analytics, cookies, local storage of answers, email, notifications, chatbots, or any feature not in this spec.
3. **Privacy by architecture.** The server keeps nothing after responding. Never write request bodies to disk, logs, error trackers, or caches. No third-party requests at runtime (no CDNs, no external fonts, no analytics). The browser must not store answers (no localStorage/sessionStorage/IndexedDB/cookies for form data).
4. **No data leakage.** Imputation, encoding that learns from data, SMOTE, scaling, and hyperparameter tuning are fitted ONLY on training data inside each fold, via a single `imblearn.pipeline.Pipeline`. The test fold is never touched by anything that learns.
5. **Model-selection rule is pre-specified** (section 6.7). Do not choose a winner by any other rule, and do not change the rule after seeing results.
6. **Language.** The UI never says "you have depression" or "you are depressed". It says "higher risk indicated" / "lower risk indicated", always with "This is a screening result, not a diagnosis." Never use red for risk. Never trivialise a higher-risk result with celebratory visuals.
7. **Reproducibility.** Fixed seeds, pinned dependency versions, one command to regenerate all outputs.
8. **Simplicity.** No frameworks beyond those listed. No build step for the frontend. No premature abstraction.
9. **Do not alter** `data/raw/Student_Mental_health.csv`. All cleaning happens in code.
10. **Do not invent facts** about institutions, phone numbers, or citations. Contact details come only from `config/support_contacts.json` (section 8.5).

## 5. Dataset specification

### 5.1 Source and licence
"Student Mental health" by MD Shariful Islam, Kaggle, licence CC0. Google Form survey at the International Islamic University Malaysia, 2020. It has been checked and is real, not synthetic. Do not search for or substitute another dataset. **[STOP AND ASK]** if you believe the file is corrupt.

### 5.2 Shape and columns (exact names; strip whitespace on load)
101 rows, 11 columns:

| Raw column | Meaning | Observed values / notes |
|---|---|---|
| `Timestamp` | form submission time | drop; not a predictor |
| `Choose your gender` | gender | Female 75, Male 26 |
| `Age` | age in years | 18 to 24; **1 missing value** |
| `What is your course?` | free-text course | **49 distinct strings**, typos (e.g. "Mathemathics"), IIUM faculty abbreviations (e.g. "Irkhs", "KENMS", "KOE") |
| `Your current year of Study` | year of study | inconsistent case: "year 1" 41, "Year 3" 19, "Year 2" 16, "year 2" 10, "year 4" 8, "year 3" 5, "Year 1" 2. Normalise to integers 1 to 4 |
| `What is your CGPA?` | CGPA band, 4.0 scale | "3.50 - 4.00" 48, "3.00 - 3.49" 43, "2.50 - 2.99" 4, "0 - 1.99" 4, "2.00 - 2.49" 2 |
| `Marital status` | marital status | No 85, Yes 16. **[ASSUMPTION]** Yes = married, No = single |
| `Do you have Depression?` | **TARGET** | No 66, Yes 35 (34.65% positive) |
| `Do you have Anxiety?` | self-reported anxiety | No 67, Yes 34 |
| `Do you have Panic attack?` | self-reported panic attacks | No 68, Yes 33 |
| `Did you seek any specialist for a treatment?` | sought specialist help | No 95, Yes 6 |

The target is a single self-reported yes/no item, not a validated clinical instrument. Positive class = "Yes" = coded 1 = "at risk".

### 5.3 Cleaning and validation (`ml/data.py`)
1. Load with pandas; strip whitespace on headers and string cells.
2. Rename columns to short snake_case names (`gender`, `age`, `course`, `year`, `cgpa_band`, `married`, `depression`, `anxiety`, `panic`, `specialist`).
3. Validate with explicit assertions that fail loudly: 101 rows; target counts 66/35; allowed value sets for each categorical column; age within 18 to 24 or missing. If any assertion fails, stop and report; do not silently adapt.
4. Map Yes/No to 1/0.
5. `year`: lowercase, extract digit, integer 1 to 4.
6. `cgpa_band`: map to ordinal 0 to 4 in the order listed in 5.2 (`0 - 1.99` = 0 … `3.50 - 4.00` = 4). Keep the band label too.
7. `age`: leave missing for in-fold imputation (do NOT impute outside the CV pipeline).
8. Produce `outputs/data_profile.md`: class balance, per-column value counts, missingness, cross-tab of each predictor against the target, correlation (phi) between binary predictors and the target. Flag any predictor strongly associated with the target (expect anxiety and panic).

### 5.4 Course grouping (`ml/features.py`, `config/faculty_groups.json`)
Group the 49 free-text courses into faculty-level categories. Canonical groups (the same list the UI dropdown shows):

```
Engineering and computing
Natural and applied sciences
Health sciences
Business and economics
Humanities and social sciences
Law
Education
Other
```

Procedure:
1. Print and inspect all unique raw course strings first.
2. Build a mapping table: raw string, normalised string, canonical group, confidence (`high`/`low`), reason. Save to `outputs/course_grouping.csv`.
3. Useful hints (IIUM "Kulliyyah" abbreviations; **verify against the actual strings, do not assume**): KOE = Engineering; KICT = Information and Communication Technology; KENMS = Economics and Management Sciences; IRKHS = Islamic Revealed Knowledge and Human Sciences; AIKOL = Laws; KAED = Architecture and Environmental Design; KOS = Science; KOED = Education; KAHS = Allied Health Sciences; KOM = Medicine; KON = Nursing; KOP = Pharmacy; KOD = Dentistry.
4. When unsure, map to `Other` and mark confidence `low`. Never guess silently.
5. After mapping, if a group has fewer than 5 rows, merge it into `Other` for modelling and record this in `docs/DECISIONS.md`. The UI still offers all canonical groups; `features.py` applies the same merge at prediction time using the group list stored in `models/metadata.json`, so the app and the model can never disagree.
6. Expose one function, `map_faculty(group_label) -> modelling_category`, used by both training and the API.

### 5.5 Feature set (nine features)
`gender`, `age`, `faculty_group`, `year`, `cgpa_band`, `married`, `anxiety`, `panic`, `specialist`.
No automated feature selection that looks at the target outside folds. Importance is analysed after the fact (section 6.8) and through ablations (section 6.9).

### 5.6 Known limitations to state, never hide
Single institution (Malaysia). n = 101. Single self-reported label. Training ages 18 to 24 only. Training years 1 to 4 only. CGPA band is on a 4.0 scale (many Nigerian universities use 5.0). No gender options beyond the two in the data. Positive class is the minority (34.65%). Write these into `docs/DATA_NOTES.md`, `outputs/model_card.md`, and the UI "About this tool" text.

## 6. ML pipeline specification

Entry point: `python -m ml.run_all`. It must run end to end from a clean checkout and regenerate every file in `outputs/` and `models/`. Target runtime: under 15 minutes on a laptop; print progress.

### 6.1 Pipeline structure (one `imblearn.pipeline.Pipeline` per model)
1. **Preprocess (`ColumnTransformer`)**
   - `age`: `SimpleImputer(strategy="median")`.
   - `year`, `cgpa_band`: already ordinal integers; pass through.
   - `gender`, `married`, `anxiety`, `panic`, `specialist`: binary 0/1; pass through.
   - `faculty_group` (after `map_faculty`): `OneHotEncoder(handle_unknown="ignore", sparse_output=False)`.
2. **SMOTE variant.** Use `SMOTENC` with the categorical column indices (binary, ordinal-as-category where appropriate, one-hot columns) so synthetic rows stay valid. If SMOTENC proves unworkable with the one-hot output, fall back to plain `SMOTE` and record why in `docs/DECISIONS.md`. Set `k_neighbors` safely (at most the minority-class count in the smallest training fold minus 1). SMOTE sits **inside** the pipeline so it only ever sees training folds. In the report this is described as "SMOTE (categorical variant, SMOTENC)".
3. **Scaling.** `StandardScaler` after SMOTE (harmless for trees, required for LR, SVM, KNN). Use the same step for all five models for consistency.
4. **Classifier.** One of the five below.

### 6.2 Models and hyperparameter grids (small on purpose; n is tiny)
| Key | Estimator | Grid |
|---|---|---|
| `logreg` | `LogisticRegression(max_iter=2000, solver="liblinear")` | `C`: 0.01, 0.1, 1, 10; `penalty`: l1, l2 |
| `svm` | `SVC(probability=True)` | `C`: 0.1, 1, 10; `kernel`: linear, rbf; `gamma`: scale |
| `tree` | `DecisionTreeClassifier(random_state=SEED)` | `max_depth`: 2, 3, 4, 5, None; `min_samples_leaf`: 1, 3, 5 |
| `knn` | `KNeighborsClassifier` | `n_neighbors`: 3, 5, 7, 9; `weights`: uniform, distance |
| `rf` | `RandomForestClassifier(n_estimators=300, random_state=SEED)` | `max_depth`: 3, 5, None; `min_samples_leaf`: 1, 3 |

Also report two baselines: `DummyClassifier("most_frequent")` and `DummyClassifier("stratified", random_state=SEED)`.
All five models use the same features and same folds. Do not tune anything on test folds.

### 6.3 Validation design (nested, repeated, stratified)
- **Outer:** `RepeatedStratifiedKFold(n_splits=5, n_repeats=10, random_state=SEED)` = 50 test folds.
- **Inner (tuning):** `GridSearchCV(..., cv=StratifiedKFold(3, shuffle=True, random_state=SEED), scoring="f1", refit=True)` fitted only on the outer training fold.
- Record the chosen hyperparameters of every outer fold in `outputs/metrics_per_fold.csv` (column `best_params`).
- Use the same outer splits for every model (generate splits once, reuse).

### 6.4 Metrics (positive class = 1 = at risk)
Per outer fold, per model: accuracy, precision, recall, F1, with `zero_division=0`. Optionally ROC-AUC as an extra column, labelled clearly as supplementary. Save:
- `outputs/metrics_per_fold.csv` (columns: model, repeat, fold, accuracy, precision, recall, f1, [roc_auc], best_params, n_train, n_test, n_test_positive).
- `outputs/metrics_summary.csv`: per model, mean and standard deviation across the 50 folds for each metric, plus the baselines.
- `outputs/confusion_matrices.csv` and a figure: for each model, sum predictions across folds within each repeat and report the mean confusion matrix per repeat (TN, FP, FN, TP). Document that every sample is tested exactly once per repeat.
Do NOT report statistical-significance claims between models; folds are not independent. Report descriptive mean ± sd only, and state that the differences are small relative to the spread if that is what the numbers show.

### 6.6 Results table for the report
`outputs/RESULTS_SUMMARY.md` (generated) contains, as Markdown tables with consistent 3-decimal formatting: class balance; preprocessing summary (what was imputed, grouped, encoded, how many synthetic samples SMOTE made per fold on average); per-model mean ± sd for the four metrics; baseline rows; confusion matrices; chosen hyperparameters (most frequently selected per model); selection outcome; sensitivity analysis; top features; and a "Warnings and caveats" section generated from the code (e.g. a feature highly correlated with the target; large sd; tiny positive count in folds).

### 6.7 Pre-specified model selection rule (fixed; implemented in `ml/select_model.py`)
1. Rank models by mean F1 (positive class) across the 50 outer folds.
2. Let the best be B with mean F1 = m and standard deviation s.
3. Any model whose mean F1 is within one standard deviation s of m is "tied".
4. Among tied models choose the simplest, in this fixed order of increasing complexity: logreg, tree, knn, svm, rf.
5. Write the full reasoning and numbers to `outputs/model_selection.md`, including the candidates, the tie set, and the winner.
If the best model does not beat the majority-class baseline on F1, say so prominently in `model_selection.md` and `RESULTS_SUMMARY.md`. Do not hide it and do not change the rule.

### 6.8 Explainability (`ml/explain.py`)
- **SHAP.** Fit the selected pipeline on all 101 rows (as for the final artifact). Compute SHAP on the transformed (post-preprocessing, pre-SMOTE) features. Use `TreeExplainer` for tree-based models; otherwise a model-agnostic explainer (`shap.Explainer` with a background of 20 k-means centres, or `KernelExplainer`). Save `shap_summary.png`, `shap_bar.png`, and `outputs/shap_mean_abs.csv` (feature, mean |SHAP|, rank). Map one-hot columns back to their parent feature (`faculty_group`) for the headline table and keep the detailed one too.
- **Permutation importance, honest version.** Inside each outer test fold, compute permutation importance of the fold's fitted model on that fold's held-out data (`n_repeats=20`), then average across folds. Save `outputs/permutation_importance.csv` and a figure. This is the cross-check against SHAP, because SHAP on the full-data fit is in-sample.
- State in the report text that explanations describe model behaviour on this dataset, not causal effects.

### 6.9 Sensitivity analyses (`ml/sensitivity.py`, small, important)
Re-run the nested CV for the selected model only, with these feature subsets:
1. all nine features (reference, copied from the main run),
2. without `anxiety` and `panic`,
3. without `specialist`,
4. without `anxiety`, `panic`, and `specialist`.
Save `outputs/sensitivity_analysis.csv` (subset, accuracy, precision, recall, F1, mean ± sd) and a figure. Add one plain-language sentence per row to `RESULTS_SUMMARY.md` describing the change. Expect anxiety and panic to dominate; report that as a finding about this dataset, not as a defect to hide.

### 6.10 Final model artifact
- Refit the selected model on all 101 rows, with its most frequently chosen hyperparameters across the outer folds (state this rule in `model_selection.md`; ties broken by the smaller value).
- Save the complete fitted pipeline with `joblib` to `models/model.joblib`.
- Save `models/metadata.json` with: model key, hyperparameters, feature order and types, ordinal and binary encodings, faculty group list and merge rule, categories seen in training, age range seen (min/max), year range seen, training date, git commit, package versions, seed, and the cross-validated scores (these are the performance estimate; the refit has none).
- Decision threshold: 0.5 on predicted probability for the positive class **[ASSUMPTION]**. Also compute and report in `RESULTS_SUMMARY.md` the precision/recall trade-off at thresholds 0.3, 0.4, 0.5, 0.6 from the pooled out-of-fold probabilities, purely as information. Do not change the deployed threshold without asking. **[STOP AND ASK]** if you think a different threshold is justified.
- Write `outputs/model_card.md`: intended use (screening aid for university students, not diagnosis), training data and limitations (section 5.6), performance (CV mean ± sd), explanations, ethical considerations, out-of-scope uses.

## 8. Web application specification

### 8.1 Stack
FastAPI backend serving a static single-page frontend (plain HTML, CSS, vanilla JavaScript; no build step, no framework, no npm runtime dependencies). One process, no database.

### 8.2 Endpoints
| Method and path | Purpose |
|---|---|
| `GET /` | serves `static/index.html` |
| `GET /static/...` | static assets |
| `POST /predict` | takes answers, returns prediction |
| `GET /health` | `{"status":"ok","model_loaded":true}` |
| `GET /api/config` | returns `copy.json`, `faculty_groups.json`, `support_contacts.json` for the frontend (no secrets, cacheable) |

### 8.3 `POST /predict` contract
Request JSON (all fields required; validate strictly with pydantic v2; reject unknown fields):
```json
{
  "gender": "female",
  "age": 21,
  "faculty_group": "Health sciences",
  "year": 2,
  "cgpa_band": "3.00-3.49",
  "married": false,
  "anxiety": true,
  "panic": false,
  "specialist": false
}
```
Validation: `gender` in {female, male}; `age` integer 16 to 60; `faculty_group` in the canonical list; `year` integer 1 to 4 (the UI's "Year 4 or above" sends 4); `cgpa_band` in {"0-1.99","2.00-2.49","2.50-2.99","3.00-3.49","3.50-4.00"}; the rest booleans. Invalid input returns HTTP 422 with field-level messages in plain English.

Response JSON:
```json
{
  "category": "higher",
  "label": "Higher risk indicated",
  "title": "Your answers suggest it may help to talk to someone",
  "message": "Lots of students feel this way, and support is available. You don't have to wait until things get worse.",
  "disclaimer": "This is a screening result, not a diagnosis.",
  "out_of_range_notes": [],
  "model_note": "Based on a model trained on survey responses from students in Malaysia, so it may be less accurate for you."
}
```
`category` is `"lower"` or `"higher"`. Do not return the raw probability to the UI. **[ASSUMPTION]** exposing a probability to a student could be misread as a diagnosis. Keep it internal.
`out_of_range_notes`: if the input falls outside what the model saw in training (age outside 18 to 24; year given as 4 when "4 or above" was chosen), include a short plain-language note (e.g. "This tool was trained on students aged 18 to 24, so the result may be less reliable at your age."). The frontend shows these under the result.

### 8.4 Privacy and security behaviour (mandatory, with tests)
- Load the model once at startup (`lifespan`); inference is a pure function of the request.
- Never log request bodies or parsed values. Run uvicorn with `--no-access-log`. Add no logging that includes payloads. Exception handlers return generic messages and must not echo input values.
- Response headers on `/predict`: `Cache-Control: no-store`. On all responses: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` disabling camera, microphone, geolocation, and a strict `Content-Security-Policy` allowing only same-origin scripts, styles, fonts, images (inline styles only if unavoidable; prefer none).
- No cookies set. No CORS (same-origin only).
- Frontend must not persist answers anywhere (no storage APIs), and must clear form state after a result is shown if the user presses "Check in again".

## 18. Appendix C: glossary (for readable code and docs)
SMOTE: Synthetic Minority Oversampling Technique; creates synthetic examples of the minority class in training data only. SMOTENC: the variant for mixed categorical and numeric features. SHAP: SHapley Additive exPlanations; attributes a prediction to features. Nested cross-validation: tuning happens in an inner loop inside each outer training fold so the outer test fold gives an honest estimate. F1: harmonic mean of precision and recall. Positive class: students who reported depression (coded 1, "at risk"). CGPA: Cumulative Grade Point Average.
